# Метрики

`GET /metrics` отдаёт метрики в текстовом формате Prometheus. Нужно право `admin`: ключ можно
передать в `X-API-Key` или как `Authorization: Bearer <ключ>` (Prometheus умеет только второе).
Определения — [app/observability/metrics.py](../app/observability/metrics.py).

```yaml
# prometheus.yml
scrape_configs:
  - job_name: llm-chat-api
    static_configs: [{targets: ["host.docker.internal:8000"]}]
    authorization: {type: Bearer, credentials: "<ключ с правом admin>"}
```

## Лог, метрика, трассировка

| | Отвечает на вопрос | Единица | Цена при росте трафика |
|---|---|---|---|
| Лог | что случилось с **этим** запросом | событие | растёт с числом запросов |
| Метрика | как дела у **всего** сервиса, и меняется ли это | агрегат: число, распределение | почти не растёт |
| Трасса | где **этот** запрос потратил время | дерево шагов одного запроса | растёт, поэтому её выборочно отбирают |

Метрика покажет, что 95-й процентиль задержки вырос вдвое с 14:00. Лог по `request_id` покажет, что
случилось с конкретным запросом. Трасса покажет, на каком шаге он потерял время.

## Три вида метрик

- **Counter** — только растёт: запросы, ошибки, токены. График строят по скорости роста
  (`rate(...[5m])`). Сброс при перезапуске процесса Prometheus понимает сам.
- **Gauge** — растёт и падает: сколько вызовов модели идёт сейчас, сколько запросов в работе.
- **Histogram** — раскладывает наблюдения по корзинам: так хранится распределение задержки.
  Процентили считаются из корзин.

## Что собирается

| Метрика | Вид | Метки | Что показывает |
|---|---|---|---|
| `http_requests_total` | counter | `method`, `path`, `status` | запросы по маршруту и коду |
| `http_request_duration_seconds` | histogram | `method`, `path` | время обработки запроса |
| `http_requests_in_flight` | gauge | | запросов в работе сейчас |
| `llm_requests_total` | counter | `model`, `endpoint`, `status` | обращения к модели по исходу (`success`, `error`, `timeout`, `cached`, `interrupted`) |
| `llm_latency_seconds` | histogram | `model`, `endpoint` | время вызова с повторами |
| `llm_ttft_seconds` | histogram | `model` | поток: время до первого куска |
| `llm_errors_total` | counter | `model`, `kind` | сбои: `timeout` или `provider_error` |
| `llm_retries_total` | counter | `model` | повторные попытки |
| `llm_tokens_total` | counter | `model`, `direction` | токены входа и выхода |
| `llm_cost_usd_total` | counter | `model` | расход по условным ценам |
| `llm_calls_in_flight` | gauge | | вызовов модели сейчас (потолок — семафор) |
| `structured_output_failures_total` | counter | `kind`, `final` | отклонённые структурированные ответы |
| `cache_hits_total`, `cache_misses_total`, `cache_errors_total` | counter | | попадания, промахи и сбои кэша |
| `rate_limit_rejections_total` | counter | | отказы по лимиту |
| `idempotent_replays_total` | counter | | повторы, отвеченные из сохранённого ответа |
| `auth_failures_total` | counter | `reason` | `invalid_key` и `insufficient_scope` |

### Метки и кардинальность

Каждая комбинация значений меток — отдельный временной ряд, поэтому метки должны иметь мало
фиксированных значений:

- **`path` — шаблон маршрута**, а не путь: `/v1/conversations/{conversation_id}`. С настоящим путём
  каждый диалог стал бы своим рядом. Неизвестные адреса — одно значение `unmatched`, иначе сканер,
  перебирающий URL, плодил бы ряды.
- **`model` берётся из тела запроса, то есть от клиента.** В виде метки он позволил бы кому угодно
  создавать новый ряд каждым запросом, придумывая имена. Поэтому именем остаётся только
  сконфигурированная модель, любое другое считается как `other`. Тест проверяет, что три выдуманных
  имени дают одно значение.
- Нет меток с идентификатором диалога, именем клиента, текстом запроса, ключом. Тест проверяет, что
  в выдаче нет ни промптов, ни ключей, ни имён клиентов.

### Что не считается задержкой модели

Попадание в кэш и оборванный поток в `llm_latency_seconds` не попадают: первое модель не вызывало,
второй не закончился. Иначе процентили занизились бы. Токены и стоимость при попадании тоже не
растут: ничего не потрачено. Они отражены в `llm_requests_total{status="cached"}`.

## Распределение, а не среднее

Среднее скрывает хвост. Если 95 запросов из 100 идут 0.4 с, а 5 — по 30 с, среднее около 1.9 с:
выглядит терпимо, хотя каждый двадцатый пользователь ждёт полминуты. Гистограмма с корзинами до
180 секунд (`LLM_BUCKETS`) показывает этот хвост, а процентиль считается так:

```promql
histogram_quantile(0.95, sum by (le) (rate(llm_latency_seconds_bucket[5m])))
```

Среднее же, посчитанное по `_sum / _count`, годится для грубой оценки и плохо — для обещаний:
SLO формулируют по процентилю («95% ответов быстрее 5 с»).

## Что говорит о деградации провайдера

| Признак | Метрика | Что это значит |
|---|---|---|
| p95 и p99 задержки растут, p50 стоит | `llm_latency_seconds` | у части запросов модель медленнее: очередь, нагрузка на GPU |
| Доля `error` и `timeout` растёт | `llm_requests_total`, `llm_errors_total` | провайдер отказывает или молчит |
| Повторы растут | `llm_retries_total` | сбои пока скрыты повторами, но уже стоят времени |
| TTFT растёт | `llm_ttft_seconds` | модель долго начинает отвечать: очередь или длинные промпты |
| `llm_calls_in_flight` упирается в предел | gauge | все слоты заняты, запросы ждут в очереди семафора |
| Задержка HTTP растёт, а `llm_latency_seconds` нет | `http_request_duration_seconds` | проблема не в модели: очередь на семафоре, база, Redis |
| Токены на запрос растут | `llm_tokens_total` / `llm_requests_total` | растёт история диалогов или длина промптов, растёт и стоимость |
| Доля `structured_output_failures_total` растёт | счётчик | модель хуже держит схему: сменили модель или изменился ввод |

Сравнение `http_request_duration_seconds` и `llm_latency_seconds` указывает на слой, где потеряно
время: разница между ними — работа самого сервиса (очередь на слоте, база, кэш).

## Пример: смешанный трафик

[scripts/metrics_traffic.py](../scripts/metrics_traffic.py): 12 разных запросов к чату, 4 одинаковых
с `temperature 0`, 3 структурированных, 1 поток и четыре заведомых отказа (неверный ключ, неверное
тело, чужое право, неизвестный адрес). Настоящая `qwen3:8b`, запись в базу отключена, Redis не
запущен, поэтому кэш, лимит и идемпотентность отступили (в этом прогоне все 4 повтора ушли к модели):

```
http_requests_total{method="POST",path="/v1/chat",status="200"} 16
http_requests_total{method="POST",path="/v1/chat",status="401"} 1
http_requests_total{method="POST",path="/v1/chat",status="422"} 1
http_requests_total{method="GET",path="/v1/usage",status="403"} 1
http_requests_total{method="GET",path="unmatched",status="404"} 1
llm_requests_total{endpoint="chat",model="qwen3:8b",status="success"} 16
llm_requests_total{endpoint="structured",model="qwen3:8b",status="success"} 3
llm_requests_total{endpoint="stream",model="qwen3:8b",status="success"} 1
llm_tokens_total{direction="input",model="qwen3:8b"} 917
llm_tokens_total{direction="output",model="qwen3:8b"} 286
auth_failures_total{reason="invalid_key"} 1
auth_failures_total{reason="insufficient_scope"} 1

llm_latency_seconds  chat: n=16, среднее 335 мс;  structured: n=3, 478 мс;  stream: n=1, 194 мс
http_request_duration_seconds  POST /v1/chat: n=18, среднее 358 мс; /v1/usage: n=1, 8 мс
```

Что видно: на `/v1/chat` пришло 18 запросов, 16 из них дошли до модели, два отклонены (401 и 422)
и модель не потревожили. Время HTTP (среднее 358 мс) складывается из времени модели (335 мс) и работы
самого сервиса вокруг неё, и по расхождению двух гистограмм видно, где потеряно время. Это один
короткий прогон на одной машине: цифры показывают, как читать метрики, а не измеряют
производительность.

## Ограничения

- Реестр метрик один на процесс. При нескольких воркерах uvicorn каждый отдаёт только свою долю, а
  Prometheus увидит случайного. Для этого есть мультипроцессный режим `prometheus_client`, он не
  включён. Сейчас один процесс на контейнер.
- Цены условные, поэтому `llm_cost_usd_total` показывает механику учёта, а не реальные деньги.
- Алертов и дашбордов в репозитории нет: метрики готовы к подключению, но не подключены.
