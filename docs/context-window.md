# Контекстное окно

Контекстное окно — максимальное число токенов, которое модель обрабатывает за один вызов:
**вход и выход вместе**. Запрос должен оставлять место для ответа:

```
оценка_входа + max_tokens ≤ окно_модели
```

## Что Ollama делает с запросом больше окна

Скрипт: [`scripts/context_experiment.py`](../scripts/context_experiment.py). `qwen3:8b` в Ollama
загружена с окном 4096 токенов.

| Ожидаемо токенов | Посчитал провайдер | Что произошло |
|---|---|---|
| 1 318 | 1 318 | поместилось |
| 3 920 | 3 918 | поместилось |
| 5 872 | **2 050** | обрезано |
| 7 823 | **2 050** | обрезано |
| 15 629 | **2 050** | обрезано |

**Ошибки нет.** Ollama молча оставляет примерно половину окна и отдаёт это модели. Модель
отвечает по части входа — например, не видя вопроса, если он был в начале, — а клиент получает
обычный `200`.

Поэтому проверка обязана быть на нашей стороне. Облачные API обычно отвечают ошибкой
`context_length_exceeded`, но и там проверка до вызова экономит время и деньги.

## Оценка токенов без токенизатора

Точный подсчёт требует токенизатора конкретной модели; эндпоинта для этого у Ollama нет
(`/api/tokenize` — 404). Используется оценка по длине текста, откалиброванная замером:

| Текст | Символов на токен |
|---|---|
| русский | 2.7–2.9 |
| английский | 5.6 |
| код | 2.9 |
| смешанный | 2.7 |

Популярное правило «4 символа на токен» для русского текста **занижает** счёт примерно на 40% — и
для проверки лимита это худшее направление ошибки. Выбрано **2.5 символа на токен**: оценка
завышает все замеренные типы текста. Плюс служебные токены шаблона чата: 10 на запрос и 8 на
каждое сообщение (запрос из одного слова стоил 17 токенов).

**Цена консервативности измерена.** Диалог, которому по факту нужно ~3200 токенов, оценён в
5173 и отклонён в режиме `reject`, хотя поместился бы. Завышение защищает от тихого обрезания,
но часть окна пропадает зря. Путь улучшения — настоящий токенизатор модели.

## Стратегии при переполнении

| `CONTEXT_OVERFLOW_STRATEGY` | Поведение |
|---|---|
| `reject` (по умолчанию) | `400 context_length_exceeded` с оценкой, резервом и лимитом; модель не вызывается |
| `truncate_oldest` | выбрасываются самые старые ходы диалога, пока запрос не поместится |

При обрезании **никогда не удаляются**:

- системные сообщения — в них инструкции;
- последнее сообщение пользователя — это сам вопрос.

Если не помещаются даже они, запрос отклоняется: резать дальше значило бы менять задачу.
Число выброшенных сообщений возвращается в ответе полем `dropped_messages`.

Проверено вживую: диалог из пяти сообщений на ~5200 оценочных токенов. `reject` → `400`;
`truncate_oldest` → выброшено 1 старое сообщение, модель ответила «Шлюз.» — ответ опирается на
оставшуюся часть истории.

## Почему по умолчанию отказ, а не обрезание

- **Тихое обрезание меняет поведение модели.** Выброшенная часть могла содержать условие задачи,
  имя пользователя или договорённость из начала диалога. Ответ станет другим, и никто не узнает
  почему.
- **Клиент знает, что важно, лучше сервера.** Отказ с понятной ошибкой оставляет решение ему.
- **Обрезание честное:** поле `dropped_messages` в ответе и запись в логе.

## Где стоит проверка

Внутри `ChatService.complete` — через этот метод проходит каждый вызов модели, включая
структурированный анализ и его повторы восстановления: с каждой попыткой их переписка растёт,
и вторая попытка может не поместиться, даже если первая помещалась. Проверка выполняется до
получения слота семафора: заведомо слишком длинный запрос не занимает место в очереди.

## Почему история не может расти бесконечно

- Каждое сообщение отправляется модели заново при каждом следующем запросе: стоимость диалога
  растёт квадратично от его длины.
- Окно конечно: рано или поздно история в него не влезет.
- Длинный контекст — это и дольше ответ, и хуже внимание модели к середине.

## Что дальше

- **Суммаризация старой части диалога** вместо выбрасывания: модель сжимает ранние ходы в
  краткую сводку. Сохраняет смысл, но стоит дополнительного вызова и сама может потерять детали.
- **Токенизатор модели** вместо эвристики — точный счёт без лишних отказов.
- **Окно на сервере шире.** Ollama позволяет поднять `num_ctx`; `qwen3:8b` поддерживает больше
  4096, ценой памяти видеокарты. Настройка приложения должна совпадать с сервером.
