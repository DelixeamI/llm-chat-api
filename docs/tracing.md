# Трассировка

Трасса — история одного запроса, span — один шаг в ней со временем начала и конца и несколькими
атрибутами. Span-ы вложены друг в друга, поэтому трасса — дерево. OpenTelemetry — стандарт для
этого; код — [app/observability/tracing.py](../app/observability/tracing.py).

## Включение

По умолчанию трассировка выключена: span-ы превращаются в пустые операции без заметной цены.

| Переменная | Назначение |
|---|---|
| `TRACING_ENABLED` | включить (по умолчанию `false`) |
| `TRACING_OTLP_ENDPOINT` | куда отправлять, например `http://localhost:4318/v1/traces` (Jaeger, OpenTelemetry Collector) |
| `TRACING_CONSOLE` | печатать span-ы в stderr: попробовать без коллектора |
| `TRACING_SAMPLE_RATIO` | доля трассируемых запросов, 0..1 |

Экспорт идёт пачками в фоне (`BatchSpanProcessor`): медленный коллектор не тормозит запросы. При
остановке приложение отправляет то, что ещё ждёт в очереди.

## Дерево запроса

Реальный запрос к `qwen3:8b` ([scripts/tracing_demo.py](../scripts/tracing_demo.py)), запись в базу
заменена пустой сессией, поэтому `db.save` почти бесплатен:

```
POST /v1/chat
http.request              136.9 ms
  prompt.build              0.0 ms
  llm.request             134.5 ms  llm.input_tokens=27 llm.output_tokens=13
    llm.attempt           133.9 ms  llm.slot_wait_ms=0.0
  db.save                   0.0 ms

POST /v1/chat/structured
http.request              537.6 ms
  llm.request             533.8 ms  llm.input_tokens=159 llm.output_tokens=52
    llm.attempt           533.3 ms  llm.slot_wait_ms=0.0
  output.validate           0.0 ms

POST /v1/chat/stream
http.request              178.3 ms
  prompt.build              0.0 ms
  llm.stream              174.9 ms  llm.ttft_ms=36.1
  db.save                   0.0 ms
```

| Span | Что измеряет | Атрибуты |
|---|---|---|
| `http.request` | весь запрос (корень) | `http.method`, `http.route`, `http.status_code`, `request.id`, `client.name` |
| `db.load_conversation` | проверка существующего диалога | |
| `prompt.build` | сборка входа: подгонка под окно | число сообщений, оценка токенов, сколько выброшено |
| `cache.lookup` | поиск в кэше | `cache.hit` |
| `llm.request` | вызов модели целиком, с повторами | модель, эндпоинт, токены, стоимость, число повторов, статус; события `retry` |
| `llm.attempt` | одна попытка | номер, `llm.slot_wait_ms` |
| `llm.stream` | весь поток | `llm.ttft_ms`, число кусков, повторы |
| `output.validate` | проверка структурированного ответа | номер попытки, `validate.failure_kind` |
| `db.save`, `db.save_usage` | запись в базу | |

## Зачем трассировка, когда есть логи и метрики

| | Что скажет о запросе на 4 секунды |
|---|---|
| Метрика | что p95 задержки вырос с 14:00 |
| Лог | что вызов модели занял 3.2 с, а запрос целиком 4.0 |
| Трасса | куда ушли остальные 0.8 с: очередь на слот модели, пауза между повторами или база |

Для запроса к LLM трасса особенно полезна, потому что это цепочка шагов с очень разной ценой. Лог
и метрика видят каждый шаг по отдельности, а трасса показывает, как они складываются в
задержку, которую заметил пользователь.

**`llm.slot_wait_ms` — время в очереди за слотом модели.** Это число нельзя увидеть ни в
замерах провайдера, ни в `llm_latency_seconds`: таймаут и задержка вызова отсчитываются после
получения слота. Под нагрузкой именно ожидание часто составляет большую часть медленного запроса.
Тест гонит два запроса через один слот и видит, что у второго `slot_wait_ms` около 100 мс (длина
первого вызова), а у первого почти ноль.

**Повторы видны как попытки:** две `llm.attempt` в одном `llm.request`, первая помечена ошибкой с
типом, между ними событие `retry` с паузой.

## Связь с логами и чужими сервисами

- **Логи.** В каждую строку лога внутри запроса добавляется `trace_id`: нашли строку по
  `request_id`, открыли трассу по `trace_id`. Тест проверяет совпадение с корневым span.
- **Заголовок `traceparent`.** Если вызывающий сервис прислал W3C `traceparent`, наш запрос становится
  частью его трассы, а не началом новой. Тест проверяет `trace_id` и идентификатор родителя.
- **Семплирование `ParentBased`.** Решение вышестоящего сервиса уважается: запрос из уже отобранной
  трассы трассируется и при нулевой доле, иначе в трассе появилась бы дыра. Тест проверяет оба
  случая.

## Что не попадает в трассу

Атрибуты — модель, числа, длительности, исходы. Нет промптов, ответов, ключей и пользовательского
текста: причины те же, что у логов ([logging.md](logging.md)).

Нашлась ловушка библиотеки. `start_as_current_span` по умолчанию записывает в статус span-а
`«ТипОшибки: сообщение»` и сохраняет исключение вместе с сообщением, а сообщение может цитировать
данные пользователя. Мы отключаем оба поведения и пишем только тип ошибки. Тест, который бросает
исключение с «секретом» внутри span, ловит это.

## Поток и контекст

Обычные span-ы делает текущими `with`-блок: он кладёт токен в контекст и снимает его при выходе.
Генератор потока может возобновиться в другом контексте, и снятие токена там падает. Поэтому для
`llm.stream`, внутри которого происходят `yield`, используется отдельный span, который не делается
текущим: родитель передаётся явно, конец ставится вручную в `finally`. Благодаря `finally` span
закрывается и при отключении клиента: незакрытый span не экспортируется, и брошенный запрос
пропал бы из трассировки. Тест проверяет это.

## Ограничения

- Нет автоинструментирования библиотек: span-ов для SQL-запросов, Redis-команд и HTTP-вызовов в
  Ollama нет. Шаги размечены вручную на уровне сервиса.
- Нет сквозной трассы клиента: заголовок `traceparent` ответом не возвращается.
- Проверено на `InMemorySpanExporter` и консольном выводе. Отправка на настоящий коллектор или в
  Jaeger не проверялась: Docker для этого этапа не был запущен.
