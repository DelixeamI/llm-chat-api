# Кэш ответов модели

Повторный одинаковый запрос к `/v1/chat` с `temperature: 0` получает ответ из Redis за
миллисекунды, не вызывая модель и ничего не тратя. Код — в
[app/services/cache.py](../app/services/cache.py).

## Что кэшируется, а что нет

| Запрос | Кэш | Почему |
|---|---|---|
| `/v1/chat`, `temperature = 0` | да | жадное декодирование: модель каждый раз выбирает самый вероятный токен |
| `/v1/chat`, `temperature > 0` | нет | клиент просил случайную выборку; повтор должен давать другой ответ |
| ответ обрезан по `max_tokens` | нет | неполный ответ отдавался бы всем до конца TTL |
| `/v1/chat/structured` | нет | годность ответа решает валидация после вызова; кэш сырого вывода сохранил бы и непригодный |

### Замер: насколько детерминирована температура 0

Один и тот же промпт «придумай название для кофейни», по 5 запусков,
[scripts/cache_experiment.py](../scripts/cache_experiment.py):

| `temperature` | разных ответов из 5 | ответы |
|---|---|---|
| 0 | 1 | «Морской Каве» × 5 |
| 0.8 | 5 | «Береговой Каве», «Волна Кофе», «Морской Бариста», … |

При температуре 0 кэш ничего не меняет для клиента: модель ответила бы так же. При 0.8 кэш
отдавал бы один случайный вариант всем, и кнопка «сгенерировать заново» перестала бы работать.

Оговорка: `temperature = 0` не гарантирует побитово одинаковый ответ. У облачных провайдеров
запросы обрабатываются пачками, и порядок операций с плавающей точкой на GPU зависит от соседей
по пачке. Поэтому одинаковый запрос изредка даёт другой ответ. Кэш в таком случае закрепляет
один из равноправных ответов. Здесь Ollama обрабатывает по одному запросу, и в замере ответы
совпали все 5 раз.

## Ключ

```python
payload = {
    "scope": "ollama:reasoning_effort=none",  # настройки провайдера вне запроса
    "model": model,
    "messages": [m.model_dump() for m in messages],  # после подгонки под окно
    "params": params.model_dump(),  # вся модель параметров
}
canonical = json.dumps(payload, sort_keys=True, ensure_ascii=False, separators=(",", ":"))
key = "llm-chat:cache:v1:" + sha256(canonical)
```

Правило: в ключ входит всё, от чего зависит ответ модели, и только это.

- **Вся история сообщений, включая системный промпт.** Для чата промпт приходит от клиента,
  поэтому его «версией» служит сам текст. Хэш содержимого лучше номера версии, который надо
  поднимать вручную: изменение промпта нельзя забыть учесть.
- **Сообщения после подгонки под окно.** Ключ строится по тому, что увидит модель. При
  `truncate_oldest` два запроса с разной старой историей, но одинаковым хвостом, получат один
  ответ, и это правильно: модель получила бы одинаковый вход.
- **Все параметры генерации целиком**, а не выбранные поля. Параметр, добавленный в
  `GenerationParams` позже, попадёт в ключ сам.
- **Настройки провайдера (`scope`).** `reasoning_effort` меняет ответ, но в запросе его нет.
  Без `scope` смена настройки продолжала бы отдавать ответы, полученные при старой.
- **Канонический JSON.** `sort_keys` и фиксированные разделители: одинаковые данные всегда дают
  одинаковые байты и одинаковый хэш.
- **SHA-256 вместо самого текста.** Ключ фиксированной длины. Текст переписки не виден в именах
  ключей, а их показывают `SCAN`, мониторинг и логи.
- **`v1` в ключе.** При смене формата значения или рецепта ключа поднимается версия. Старые
  записи никто не читает, и они истекают сами.

Кэш точный, по совпадению байтов. «Привет» и «Привет!» — разные ключи. Пробелы по краям
сообщения не мешают попаданию: их убирает валидация запроса ещё до построения ключа.
Семантический кэш по близости эмбеддингов попадал бы чаще, но иногда отдавал бы ответ на
похожий, а не тот же вопрос.

## TTL и инвалидация

Запись живёт `RESPONSE_CACHE_TTL_SECONDS`, по умолчанию час. Значение и срок жизни ставятся
одной командой `SET key value EX 3600`.

Ключ меняется сам, когда меняется вход, но есть изменения, которые ключ не видит:

- **Обновление модели под тем же именем.** После `ollama pull qwen3:8b` веса новые, а ключ
  прежний. Старые ответы отдаются до конца TTL. Именно TTL ограничивает, насколько устаревшим
  может быть ответ. Точнее было бы добавить в `scope` дайджест модели из `/api/show`.
- **Ручная очистка** — удалить ключи `llm-chat:cache:*` через `SCAN` или поднять
  `CACHE_VERSION`.

Короткий TTL — ещё и ограничение хранения: в Redis лежат тексты ответов, и через час их там нет.

Память: по замеру дня 29 запись со значением 1000 байт занимает около 1.2 КБ. В 128 МБ помещается
порядка 100 000 ответов. При нехватке памяти `allkeys-lru` вытесняет давно не запрошенные.

## Что происходит при попадании

- Модель не вызывается, ответ приходит с `"cached": true`.
- `usage` описывает генерацию, которая когда-то дала этот ответ.
- Сообщения пишутся в PostgreSQL как обычно: для клиента обмен репликами состоялся, и он
  должен быть в истории диалога.
- В `usage_logs` строка **не пишется**: журнал учитывает расход, а попадание ничего не
  потратило. Поэтому отчёт о стоимости и прогноз на месяц сами учитывают экономию от кэша.

## Попадания и промахи

Счётчики `llm-chat:stats:cache:hits` и `...:misses` увеличиваются атомарным `INCR` при каждом
обращении к кэшу. Запросы, которые кэшировать нельзя, до кэша не доходят и не считаются.

```
GET /v1/cache/stats
{"enabled": true, "hits": 15, "misses": 5, "hit_rate": 0.75}
```

Счётчики лежат в Redis, а не в памяти процесса: при нескольких воркерах Uvicorn каждый видел бы
только свою долю. Это единственные ключи сервиса без TTL. Их всего два, и они не растут. В неделю
6 их заменят метрики Prometheus.

## Если Redis недоступен

Кэш — оптимизация, поэтому его отказ не должен ломать запросы. Любая ошибка Redis превращается в
промах, и отвечает модель.

Но у простого «ловим ошибку — идём к модели» есть цена. Каждый запрос во время аварии ждал бы
два таймаута по 0.5 с — на чтение и на запись — и писал бы два предупреждения в лог. Поэтому после
первой ошибки кэш пропускается 30 секунд, а потом пробует снова. Это упрощённый размыкатель
цепи (circuit breaker). Проверено тестами `test_redis_outage_falls_back_to_model_and_pauses_cache`
и `test_cache_is_retried_after_cooldown`.

`GET /v1/cache/stats` без Redis отвечает `503 redis_unavailable`: у статистики нет запасного
источника.

## Когда кэш делает неправильно или опасно

- **Недетерминированный запрос.** Кэш подменяет случайную выборку одной замороженной.
- **Вход модели, которого нет в ключе.** Если сервер добавит в промпт данные конкретного
  пользователя — профиль, документы из RAG, результаты инструментов, текущее время — и не
  включит их в ключ, другой пользователь получит чужой ответ. Это утечка данных. Сейчас ключ
  содержит весь вход модели, поэтому одинаковый ответ отдаётся только на одинаковый вход.
- **Утечка через время ответа.** Ответ за 2 мс вместо 450 мс показывает, что кто-то уже
  отправлял точно такую же переписку. Кэш общий для всех клиентов. Когда появятся API-ключи
  (день 32), нужно решить, разделять ли кэш по клиентам.
- **Хранение.** Ответ может пересказывать персональные данные из вопроса. Он живёт в Redis до
  истечения TTL, на диск не пишется.
- **Одновременные промахи.** Два одинаковых запроса, пришедшие одновременно, оба не найдут
  записи и оба вызовут модель. Модель отработает дважды, хотя хватило бы одного вызова. Лечится
  блокировкой на ключ (`SET NX`), это близко к идемпотентности дня 34. Пока не сделано.

## Замер

20 запросов к `qwen3:8b`, выбранных случайно из 5 вопросов поддержки, `temperature: 0`,
Redis в Docker:

| | Значение |
|---|---|
| попадания / промахи | 15 / 5 |
| доля попаданий | 0.75 |
| промах, медиана | 445 мс |
| попадание, медиана | 1.9 мс |

Скрипт не пишет в PostgreSQL. Через настоящий HTTP-сервер тот же вопрос занял 133 мс при
промахе и 14 мс при попадании. На Redis из этих 14 мс приходится около 2 мс, как в скрипте.
Остальное — HTTP и транзакция с сообщениями диалога в PostgreSQL. В `usage_logs` после двух запросов прибавилась одна строка, TTL
записи — 3599 с.

Попадание в 230 раз быстрее. Промах почти ничего не теряет: к вызову модели добавляются `GET`,
`INCR` и `SET`, около 2.5 мс на Docker Desktop, то есть меньше 1% от 445 мс. Доля попаданий
целиком зависит от нагрузки: 5 уникальных вопросов из 20 — это 5 неизбежных промахов. Для чата
с уникальными разговорами доля будет близка к нулю. Кэш окупается на повторяющихся запросах:
FAQ, классификация, одинаковые системные промпты.

## Тесты

- [test_cache.py](../tests/test_cache.py) — поведение через фейковый Redis. Проверяются ключ
  (равенство и чувствительность к каждому входу), попадание без вызова модели и без строки в
  журнале расхода, TTL, обход при `temperature > 0` и обрезанном ответе, повреждённая запись,
  авария Redis и пауза, счётчики, `/v1/cache/stats`.
- [test_redis_integration.py](../tests/test_redis_integration.py) — запись, чтение, TTL и
  счётчики на настоящем Redis.

Фейковый Redis записывает TTL, но не выполняет его: истечение ключа — поведение сервера, и
проверяется оно на настоящем Redis.
