# Три главных компромисса

Решение полезно, когда ясно, что отвергнуто и чем оплачено. Здесь три решения, которые сильнее всего
определяют поведение сервиса. Остальные описаны в
[architecture.md](architecture.md) и документах по темам.

## 1. Redis-возможности отказывают «в открытую», а не «в закрытую»

**Решение.** Кэш, ограничение частоты и идемпотентность при недоступном Redis не останавливают
запросы: кэш даёт промах, лимит пропускает, идемпотентность отключается. После первой ошибки Redis
не опрашивается 30 секунд.

**Что отвергнуто.**

| Вариант | Почему не он |
|---|---|
| Fail closed: недоступный Redis — отказ на `/v1/chat` | потеря кэша стала бы потерей всего сервиса; все три возможности — оптимизация и защита, а не условие правильности |
| Ретраи Redis до успеха | каждый запрос ждал бы таймаут Redis, а аварийный Redis лишь сильнее нагружался бы |
| Проверять Redis на каждый запрос без паузы | в аварии каждый запрос платил бы 2 × 0.5 с и писал бы два предупреждения |

**Цена.** Пока Redis лежит, нет защиты: лимит не работает, повторный запрос может создать дубль,
каждый одинаковый запрос стоит модели. Для платёжной операции или защиты от подбора пароля выбор
был бы обратным (fail closed). Здесь Redis ничего ценного не хранит, а семафор вокруг модели
по-прежнему ограничивает ущерб. Видно это по метрикам (`cache_errors_total`) и `/ready` (`degraded`).

**Как проверено.** `test_every_redis_feature_degrades_without_failing_the_request` и тесты каждой
возможности по отдельности; [failure-scenarios.md](failure-scenarios.md).

## 2. Структурированный ответ: схема, проверка и ограниченное восстановление

**Решение.** Схема из Pydantic уходит провайдеру как JSON Schema (грамматика ограничивает
генерацию), ответ всё равно проверяется в приложении, при ошибке модель получает свой ответ и
нарушенное правило и пробует один раз. Обрыв по лимиту токенов не повторяется.

**Что отвергнуто.**

| Вариант | Результат замера (12 обращений, `qwen3:8b`) | Почему не он |
|---|---|---|
| Просьба «верни JSON» | 0 годных из 12 | все ответы в markdown-обёртке, категории выдуманы |
| JSON mode | 1 годный из 12 | синтаксис гарантирован, схема нет |
| Только грамматика, без проверки | `confidence: 150` при максимуме 1 прошёл | грамматика не держит диапазоны и смысл |
| Повторять до успеха | | без предела стоимость неограниченна; модель стабильно ошибается там, где ошиблась один раз |
| Чинить ответ кодом (подбирать категорию по похожему слову) | | однажды «починит» неправильно и скроет проблему |

**Цена.** Повтор стоит примерно вдвое больше входных токенов; два уровня повторов (сетевой и
восстановления) перемножаются: до шести вызовов провайдера на один запрос. Выбрано так потому, что
на замере восстановление исправило 3 из 3, а граница в один повтор ограничивает стоимость.

**Как проверено.** [structured-output.md](structured-output.md), тесты `test_analysis.py`,
замеры в `docs/experiments/`.

## 3. Свой контроль контекстного окна вместо доверия провайдеру

**Решение.** До вызова модели оценка входа плюс `max_tokens` сравнивается с окном; по умолчанию —
отказ 400, по настройке — обрезание старых ходов с полем `dropped_messages`.

**Что отвергнуто.**

| Вариант | Почему не он |
|---|---|
| Положиться на ошибку провайдера | замер показал, что Ollama **не** отвечает ошибкой: 5872, 7823 и 15 629 токенов молча стали 2050, ответ 200 |
| Всегда молча обрезать | выброшенная часть могла содержать условие задачи, ответ изменится без видимой причины |
| Точный токенайзер модели | у Ollama нет эндпоинта подсчёта токенов; тянуть токенайзер ради проверки — лишняя зависимость |
| Правило «4 символа на токен» | замер: русский — 2.7–2.9, поэтому правило занижает на ~40% |

**Цена.** Оценка (2.5 символа на токен) консервативна: запрос на ~3200 реальных токенов был оценён в
5173 и отклонён, хотя поместился бы. Более точный путь — токенайзер модели.

**Как проверено.** [context-window.md](context-window.md), `test_context.py`, скрипт
`scripts/context_experiment.py`.

## Ещё несколько решений коротко

| Решение | Альтернатива | Почему так |
|---|---|---|
| Вызов модели без открытой транзакции | одна транзакция на весь запрос | не держать соединение пула минуты и не мешать autovacuum |
| Порядок сообщений по `seq` | по `created_at` | `now()` — время начала транзакции, оба сообщения обмена получают одно время |
| Кэш только при `temperature 0`, приватный по клиенту | общий кэш всех клиентов | подмена разных ответов одним и утечка через время ответа |
| Лимит скользящим окном в Lua | `INCR` + `EXPIRE` | нет граничного всплеска и гонки «прочитал, записал» |
| Чужой диалог — 404, а не 403 | 403 | 403 подтверждает существование идентификатора |
| Готовность без провайдера LLM | включить его | отказ провайдера вывел бы из балансировки все экземпляры |
| Миграции отдельным сервисом | при старте приложения | несколько реплик не гоняются за одной схемой |
