# Учёт токенов и стоимости

## Журнал `usage_logs`

Одна строка на каждый запрос, потративший токены модели:

| Колонка | Смысл |
|---|---|
| `endpoint` | `chat` или `structured` |
| `model` | модель, которой был запрос |
| `conversation_id` | диалог, если есть; при удалении диалога обнуляется, запись остаётся |
| `input_tokens`, `output_tokens` | по данным провайдера, сумма по всем попыткам |
| `total_tokens` | вычисляемая колонка базы: `input_tokens + output_tokens` |
| `attempts` | сколько генераций потрачено |
| `status` | `success` или `failed` |
| `cost_usd` | стоимость на момент вызова; `null`, если у модели не было цены |

Почему отдельный журнал, если токены уже есть в `messages`: сообщения описывают переписку, а
журнал — деньги. В журнал попадают вызовы, которые не стали сообщениями: структурированный
анализ и отклонённые генерации. Неудачный запрос тоже оплачен, и без него ошибки выглядели бы
бесплатными.

## Токены: входные и выходные

- **Входные** — всё, что модель читает: системный промпт, история, текст пользователя.
- **Выходные** — всё, что модель генерирует.
- **Числа берутся у провайдера**, а не считаются локально: счёт выставляют по его подсчёту.
  Локальная оценка нужна только заранее, до вызова, — для проверки контекстного окна.

## Формула стоимости

```
cost_usd = input_tokens  × input_price_per_million  / 1 000 000
         + output_tokens × output_price_per_million / 1 000 000
cost_rub = cost_usd × usd_to_rub
```

**Цены на вход и выход разные**, выход обычно в 3–8 раз дороже. Чтение промпта обрабатывается
параллельно одним проходом, а каждый выходной токен — это отдельный последовательный шаг
модели. Поэтому при оценке затрат важно соотношение входа и выхода, а не только сумма.

**Деньги — в `Decimal`, в базе — `Numeric(14, 8)`.** `float` не представляет точно даже
`0.1`, и ошибки округления накапливаются при суммировании миллионов строк.

## Решения

- **Стоимость фиксируется в момент вызова.** Цены меняются; пересчёт истории по новому тарифу
  переписал бы то, что уже было потрачено.
- **Рубли считаются при построении отчёта** по текущему курсу `USD_TO_RUB`. Курс в ответе
  указан явно. Компромисс: смена курса пересчитывает историю в рублях. Если нужна рублёвая
  бухгалтерия, курс надо хранить в каждой строке так же, как цену.
- **Неизвестная цена — это `null`, а не ноль.** Отчёт показывает `unpriced_requests`. Ноль
  выглядел бы как бесплатный запрос и тихо занижал бы расходы.
- **Агрегация — в базе.** `SUM ... GROUP BY model` вместо чтения всех строк в Python.

## Цены в проекте — условные

Локальная модель не выставляет счёт за токены: её стоимость — видеокарта и электричество.
Для демонстрации учёта `qwen3:8b` по умолчанию оценена в `$0.05` за миллион входных и `$0.40`
за миллион выходных токенов. Это условные цифры, а не тариф какого-либо провайдера.
Переопределяются переменными окружения:

```bash
MODEL_PRICES='{"qwen3:8b": {"input_per_million_usd": "0.05", "output_per_million_usd": "0.40"}}'
USD_TO_RUB=95
```

## Эндпоинты

```
GET /v1/usage?days=30        токены и число запросов по моделям
GET /v1/usage/cost?days=30   стоимость, среднее за день и прогноз на месяц
```

Прогноз на месяц = средний расход за день в окне × 30. Он предполагает, что трафик останется
прежним, и на коротком окне шумный.

## Оценка месячных расходов по трафику

Когда истории ещё нет, расход оценивают из ожидаемого трафика и распределения токенов:

```
месяц = запросов_в_день × 30 × (средний_вход × цена_входа + средний_выход × цена_выхода) / 1 000 000
```

Пример по замерам этого проекта: структурированный анализ одного обращения тратит около 146
входных и 60 выходных токенов. При 5 000 обращений в день и ценах `$0.15` / `$0.60` за миллион:

```
за запрос: (146 × 0.15 + 60 × 0.60) / 1 000 000 = $0.0000579
за месяц:  5 000 × 30 × 0.0000579 ≈ $8.7
```

Поправки, которые легко забыть:

- **Повторы восстановления.** Каждое восстановление примерно удваивает вход: второй запрос
  несёт первый ответ и сообщение об ошибке. Замер: 433 входных токена против 146.
- **Рост истории в чате.** Каждое новое сообщение повторно отправляет всю предыдущую
  переписку: вход растёт с длиной диалога, и средний вход берётся не из первого сообщения.
- **Хвост распределения.** Средняя скрывает длинные запросы; бюджет считают по перцентилю, а не
  только по среднему.
