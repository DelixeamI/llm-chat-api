# Ограничение частоты запросов

Каждый клиент может сделать не больше **20 запросов в минуту** к эндпоинтам, которые тратят модель:
`/v1/chat`, `/v1/chat/stream`, `/v1/chat/structured`. Лимит общий на все три и считается по имени
клиента (то есть по ключу, а не по IP). Код — [app/services/ratelimit.py](../app/services/ratelimit.py),
зависимость — `enforce_rate_limit` в [app/api/security.py](../app/api/security.py).

Настройки: `RATE_LIMIT_ENABLED`, `RATE_LIMIT_REQUESTS=20`, `RATE_LIMIT_WINDOW_SECONDS=60`.

## Ответ при превышении

```
HTTP/1.1 429 Too Many Requests
Retry-After: 37
X-RateLimit-Limit: 20
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 37

{"error": "rate_limit_exceeded", "detail": "limit of 20 requests per 60 s exceeded, retry in 37 s"}
```

- `Retry-After` — через сколько секунд повторить (стандартный заголовок, RFC 6585).
- `X-RateLimit-Limit`, `-Remaining`, `-Reset` приходят и с успешными ответами, поэтому клиент
  видит остаток заранее, а не только упираясь в отказ. `Reset` — секунды до того, как из окна уйдёт
  самый старый учтённый запрос.
- Отказ приходит до вызова модели и до записи в БД: отклонённый запрос ничего не стоит.

## Лимит запросов и лимит конкурентности

| | Семафор (`LLM_MAX_CONCURRENCY`) | Rate limit |
|---|---|---|
| Что считает | вызовы модели, идущие **прямо сейчас** | запросы клиента **за период** |
| Что защищает | модель от одновременной перегрузки | бюджет и других клиентов от одного |
| Где живёт | память процесса | Redis, общий для процессов |
| Реакция | запрос ждёт слот | 429 сразу |

Нужны оба, потому что они закрывают разные дыры:

- 20 разрешённых запросов могут прийти в одну секунду. Лимит их пропустит, семафор выстроит в
  очередь по 5. Без семафора все 20 одновременно ударили бы по модели.
- Пять слотов семафора обработают сотни коротких запросов в минуту, если они идут по очереди. Без
  rate limit один клиент займёт все слоты навсегда и израсходует бюджет.

## Алгоритм: скользящее окно

Каждый допущенный запрос — запись в отсортированном множестве Redis с временем в качестве оценки.
При новом запросе записи старше окна удаляются, остальные считаются: меньше лимита — допустить и
записать, иначе отказать.

**Почему не простой счётчик `INCR` + `EXPIRE` (фиксированное окно).** У него есть граничный всплеск:
клиент тратит весь лимит в конце одного окна и ещё раз в начале следующего, то есть двойной лимит
за секунды. Скользящее окно считает последние 60 секунд от текущего момента, и границы нет. Цена:
память растёт с лимитом (20 записей на клиента), что здесь пренебрежимо.

Другие варианты, которые не выбраны: token bucket (допускает плановые всплески, сложнее объяснить
клиенту) и счётчик по скользящей оценке из двух окон (дешевле по памяти, но приблизительный).

## Атомарность

Алгоритм — это «прочитать, сравнить, записать». Если делать это тремя командами из приложения, то
два параллельных запроса оба прочитают «19» и оба пройдут. Такая гонка не видна в тестах с одним
запросом и проявляется только под нагрузкой.

Redis выполняет **одну команду целиком**, не вклиниваясь между командами других клиентов. Поэтому
весь алгоритм собран в один Lua-скрипт (`SLIDING_WINDOW`): Redis выполняет скрипт без чередования
с другими командами, и в нём нечему гоняться. Детали:

- **Время берётся у Redis** (`TIME`), а не у приложения: процессы с чуть разными часами согласуются
  об одном окне.
- **Уникальный элемент множества:** время плюс случайная приставка. Иначе два запроса в одну
  миллисекунду записались бы как один, и клиент получил бы лишний.
- **`PEXPIRE` на ключ:** ключ исчезает сам, когда клиент замолчал, и память не копится.
- Скрипт регистрируется через `register_script`: redis-py шлёт `EVALSHA` и при необходимости
  сам догружает текст скрипта.

## Если Redis недоступен

Лимитер **пропускает запросы** (fail open) и 30 секунд не обращается к Redis. Обоснование: лимит
защищает бюджет, а не корректность, и отказ всем клиентам из-за сбоя кэш-слоя превратил бы частичную
аварию в полную. Пока лимита нет, число одновременных вызовов модели всё равно ограничено семафором.

Для лимита, который защищает от злоупотребления (платный API, вход по паролю), выбор был бы
обратным: fail closed. Здесь цена ошибки другая.

## Что считается и что нет

- **Считаются только опознанные клиенты.** Лимитер стоит после проверки ключа, поэтому поток
  запросов с чужими ключами не расходует лимит настоящего клиента, а запрос с нехваткой прав (403)
  не считается.
- Чтение истории, создание пустого диалога, `/health` не ограничиваются: лимит защищает то, что
  стоит денег.
- **Отказ тоже не записывается в окно:** клиент, который упёрся в лимит и продолжает слать запросы,
  не отодвигает свой сброс.

## Ограничения

- Лимит — на запросы, а не на токены. Один запрос на 8000 токенов и один на 10 токенов считаются
  одинаково. Лимит по стоимости или токенам был бы точнее и сложнее.
- Лимит один на все эндпоинты и для всех клиентов; свои лимиты на клиента не заданы.
- Подбор неверных ключей не ограничивается: без опознанного клиента считать нечего.

[test_ratelimit.py](../tests/test_ratelimit.py) — скрипт на `fakeredis` (он исполняет настоящий Lua
по семантике Redis): допуск до лимита и отказ, изоляция клиентов, скольжение окна, 60 параллельных
запросов при лимите 20, два запроса в одну миллисекунду, истечение ключа, отказ Redis; по HTTP —

лимит, fail open.

[test_redis_integration.py](../tests/test_redis_integration.py) повторяет атомарность, истечение

ровно 20. Скрипт [scripts/ratelimit_experiment.py](../scripts/ratelimit_experiment.py) сравнивает
наивный «прочитал, записал» со скриптом на 200 параллельных запросах.
