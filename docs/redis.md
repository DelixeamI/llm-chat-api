# Redis

Redis в проекте нужен для трёх конкретных задач недели 5:

| Задача | Что хранится | День |
|---|---|---|
| Кэш ответов модели | готовый ответ на детерминированный запрос | 30 |
| Ограничение частоты запросов | счётчик запросов ключа за окно времени | 33 |
| Идемпотентность | маркер «запрос выполняется» и готовый ответ | 34 |

Все три — временные данные с ограниченным сроком жизни. Если их потерять, сервис продолжит
работать: кэш прогреется заново, счётчики начнутся с нуля, а в худшем случае повторный запрос
будет выполнен ещё раз.

## Что такое Redis

Redis — хранилище «ключ — значение», которое держит все данные в оперативной памяти. Отсюда
его свойства:

- **Скорость.** Команда выполняется за микросекунды: нет обращения к диску и разбора SQL.
  Задержку почти целиком составляет сеть.
- **Команды выполняются по одной.** Сервер обрабатывает команды в одном потоке, поэтому каждая
  отдельная команда атомарна. `INCR` двух клиентов одновременно даст ровно +2, без гонки
  «прочитал — прибавил — записал». На этом построим ограничение частоты в день 33.
- **Срок жизни ключа (TTL).** Ключ удаляется сам через заданное время. Для кэша и временных
  маркеров это главный механизм очистки.
- **Объём ограничен памятью.** Когда память кончается, Redis либо отказывает в записи, либо
  вытесняет ключи — в зависимости от политики.

## Почему Redis не заменяет PostgreSQL

| | PostgreSQL | Redis в этом проекте |
|---|---|---|
| Долговечность | запись подтверждена — значит, на диске | сохранение отключено: перезапуск стирает всё |
| Модель данных | таблицы, связи, внешние ключи, ограничения | ключи и значения, связей нет |
| Запросы | SQL: фильтры, соединения, агрегаты | доступ по ключу; поиск по значению — перебор |
| Транзакции | атомарность, откат, изоляция | `MULTI` выполняет пачку команд подряд, но отката нет |
| Объём | ограничен диском | ограничен памятью: здесь 128 МБ |

Правило проекта: **в Redis лежит только то, что можно потерять**. Диалоги, сообщения и журнал
расхода остаются в PostgreSQL. Источник истины — база, Redis — ускоритель и хранилище
счётчиков.

Redis умеет сохранять данные на диск (снимки RDB и журнал AOF), но это не делает его
реляционной базой, а для наших задач не нужно. Поэтому сохранение выключено: меньше нагрузки
на диск и нет иллюзии, что там лежит что-то ценное.

## Конфигурация контейнера

```yaml
command:
  - redis-server
  - --save
  - ""                   # без снимков на диск
  - --appendonly
  - "no"                 # без журнала операций
  - --maxmemory
  - 128mb                # потолок памяти
  - --maxmemory-policy
  - allkeys-lru          # при нехватке памяти вытеснять давно не использованные ключи
ports:
  - "127.0.0.1:${REDIS_PORT:-6379}:6379"
```

- **`allkeys-lru`** — при нехватке памяти Redis удаляет ключи, к которым дольше всего не
  обращались. Для кэша это правильное поведение. Политика по умолчанию, `noeviction`, в той же
  ситуации начала бы отвечать ошибкой на каждую запись.
- **Порт только на `127.0.0.1`.** Пароля у локального Redis нет. Без адреса в `ports` Docker
  публикует порт на всех интерфейсах, и Redis был бы доступен из локальной сети. Та же правка
  сделана для PostgreSQL.

## Пространство имён ключей

Каждый ключ сервиса начинается с общего префикса, дальше идут задача, версия формата и
идентификатор:

```
llm-chat:cache:v1:3f2a...        кэш ответа
llm-chat:ratelimit:...           счётчик ограничения частоты (день 33)
```

Ключи строит одна функция, `make_key` в [app/kv/client.py](../app/kv/client.py). Зачем:

- один Redis часто делят несколько сервисов, и префикс не даёт им перезаписать ключи друг
  друга;
- по префиксу можно найти или удалить все ключи одной задачи: `SCAN MATCH llm-chat:cache:*`;
- версия в ключе позволяет сменить формат значения: новый код читает `v2`, старые записи `v1`
  никто не читает, и они сами истекают по TTL.

`KEYS llm-chat:*` для этого не подходит: команда перебирает всю базу за один раз и блокирует
сервер на время перебора. `SCAN` отдаёт ключи порциями.

## TTL

```python
await redis.set(key, value, ex=3600)  # значение и срок жизни — одной командой
```

Значение и срок жизни задаются одной командой. Вариант `SET`, а затем `EXPIRE` — это две
команды. Если процесс упадёт между ними, останется ключ без срока жизни, который никогда не
удалится.

`TTL` и `PTTL` возвращают оставшееся время. Отрицательные ответы означают разное: `-1` — ключ
есть, но срока жизни у него нет, `-2` — ключа нет. Тест
[test_redis_integration.py](../tests/test_redis_integration.py) проверяет, что ключ с TTL 100 мс
действительно исчезает.

## Клиент и пул соединений

Клиент создаётся один раз при старте приложения в `lifespan` и закрывается при остановке — так
же, как клиент модели и движок базы.

```python
pool = BlockingConnectionPool.from_url(
    url,
    max_connections=20,  # REDIS_MAX_CONNECTIONS
    timeout=0.5,  # ожидание свободного соединения
    socket_connect_timeout=0.5,  # подключение
    socket_timeout=0.5,  # одна команда
)
return Redis.from_pool(pool)
```

- **Пул** держит открытые соединения и раздаёт их командам. Новое TCP-соединение на каждую
  команду стоит заметно дороже самой команды (замер ниже).
- **Блокирующий пул.** Когда все соединения заняты, следующая команда ждёт, пока одно
  освободится, но не дольше `timeout`. Обычный пул в той же ситуации сразу падает с ошибкой
  `Too many connections`: короткий всплеск нагрузки превратился бы в ошибки вместо небольшой
  очереди. Число соединений от процесса к Redis в обоих случаях ограничено.
- **Таймауты по 0.5 с.** Redis отвечает быстрее миллисекунды. Если ответа нет полсекунды,
  Redis недоступен, и ждать дольше бессмысленно: запрос к кэшу не должен задерживать ответ
  пользователю.
- **При создании клиент не подключается.** Соединения открываются при первой команде. Поэтому
  приложение стартует, даже когда Redis лежит, а каждая функция сама решает, как работать без
  него. Для кэша ответ простой: без кэша (день 30).

### Найденная ошибка: `Redis(connection_pool=pool)` не закрывает соединения

Первая версия создавала клиент как `Redis(connection_pool=pool)`. Интеграционный тест упал с
`ResourceWarning: unclosed Connection`: pytest в проекте превращает предупреждения в ошибки.
Клиент, получивший чужой пул, считает, что пулом владеет кто-то другой, и `aclose()` его не
закрывает. При остановке приложения соединения оставались открытыми. `Redis.from_pool(pool)`
передаёт пул клиенту во владение, и `aclose()` закрывает всё.

## Замеры

Скрипт [scripts/redis_experiment.py](../scripts/redis_experiment.py), Redis 8 в Docker Desktop
на Windows.

**Пул или новое соединение на команду.** Последовательные `GET`, медиана четырёх прогонов:

| Вариант | мс на операцию |
|---|---|
| общий клиент с пулом | 0.81 |
| новое соединение на каждую команду | 7.38 |

Новое соединение делает операцию в 9 раз медленнее. Даже 0.8 мс для Redis много: почти всё
это время уходит на проброс порта Docker Desktop между Windows и WSL2. На Linux и внутри сети
Docker задержка в разы меньше.

У варианта «соединение на команду» обнаружилась вторая цена. Первый прогон оставил в системе
**7688 сокетов в состоянии `TIME_WAIT`**: после закрытия TCP-соединения клиентская сторона
держит порт ещё несколько минут. Повторный запуск скрипта сразу после первого упал на
подключении. Под реальной нагрузкой так кончаются локальные порты, и сервис перестаёт
подключаться к Redis вообще.

**Размер пула.** 1000 одновременных `GET`:

| `max_connections` | открыто соединений | общее время, мс |
|---|---|---|
| 1 | 1 | 853 |
| 10 | 10 | 443 |
| 50 | 50 | 642 |

- Пул действительно держит границу: соединений открыто ровно столько, сколько разрешено.
  Остальные команды ждут в очереди.
- Больше соединений — не всегда быстрее. Redis выполняет команды в одном потоке, поэтому
  параллельность нужна только для того, чтобы скрыть сетевую задержку. После этого каждое
  соединение добавляет лишь накладные расходы: 50 соединений оказались медленнее 10.

**Память.** 10 000 ключей со значением 1000 байт заняли по 1193 байта на ключ: около 19%
сверху уходит на сам ключ и служебные структуры. В 128 МБ помещается около 100 000 таких
записей. Этот расчёт понадобится для кэша.

## Недоступный Redis

Тест [test_kv_client.py](../tests/test_kv_client.py) проверяет, что при недоступном Redis первая
команда падает с `RedisError` быстрее секунды. В ручном замере при таймауте 0.2 с ошибка пришла
через 0.22 с. На Windows отказ в
соединении не приходит мгновенно: система повторяет попытку, поэтому срабатывает именно
таймаут подключения. Без таймаута каждая команда ждала бы секунды.

## Тесты

- Модульные тесты ([test_kv_client.py](../tests/test_kv_client.py)) проверяют, что клиент
  создаётся без подключения и быстро падает, если Redis недоступен. Сервер для них не нужен.
- Интеграционные тесты ([test_redis_integration.py](../tests/test_redis_integration.py))
  работают с настоящим Redis: связь, истечение TTL, префиксы, очередь в пуле. Им нужен
  запущенный контейнер; без него тесты пропускаются. Они используют отдельную логическую базу
  15 и очищают её перед каждым тестом. Эксперимент использует базу 14. Данные разработки в
  базе 0 не затрагиваются.
