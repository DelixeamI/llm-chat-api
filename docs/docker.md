# Запуск в контейнерах

Весь стек — приложение, PostgreSQL, Redis — поднимается одной командой из чистого окружения.

```bash
cp .env.example .env     # затем добавьте API_KEYS (см. ниже)
docker compose up --build
```

С настоящей моделью: нужна Ollama на хосте. С заглушкой модели (без GPU, для пробы и для CI):

```bash
COMPOSE_LLM_URL=http://fake-llm:9000/v1 docker compose --profile fake-llm up --build
```

Когда приложение запущено на хосте (`uvicorn --reload`), а в контейнерах нужны только зависимости:

```bash
docker compose up -d postgres redis
```

## Что поднимается

| Сервис | Роль | Порядок |
|---|---|---|
| `postgres` | база данных | первым, с `healthcheck` |
| `redis` | кэш, лимит, идемпотентность | параллельно, с `healthcheck` |
| `migrate` | разовая задача `alembic upgrade head`, затем выходит | после `postgres` |
| `api` | приложение на `127.0.0.1:8000` | после `postgres` и `redis` готовы и `migrate` успешно завершён |
| `fake-llm` | заглушка модели, только в профиле `fake-llm` | |

### Зависимости между сервисами

`depends_on` с условиями вместо простого порядка запуска. Порядок «контейнер запущен» ничего не
гарантирует: PostgreSQL принимает соединения не сразу после старта процесса. Поэтому условия:

- `service_healthy` — ждать, пока `healthcheck` сервиса (`pg_isready`, `redis-cli ping`) станет
  зелёным;
- `service_completed_successfully` — ждать, пока разовая задача миграций завершилась с кодом 0.
  Если миграция упала, `api` не стартует вообще: лучше не запуститься, чем работать на схеме,
  которая не соответствует коду.

**Миграции — отдельный сервис, а не шаг при старте приложения.** При нескольких репликах `api`
каждая стала бы мигрировать одновременно и гоняться за одну и ту же схему. Одна задача выполняется
один раз до всех реплик.

### Сеть между сервисами

Compose создаёт общую сеть, и контейнеры обращаются друг к другу **по имени сервиса**:
`postgres:5432`, `redis:6379`. Не `127.0.0.1`: внутри контейнера это он сам. Поэтому у `api` и
`migrate` переопределены `DATABASE_URL` и `REDIS_URL`, а значения из `.env` для запуска на хосте
(`127.0.0.1:5433`) на контейнеры не влияют. Порты PostgreSQL и Redis опубликованы на хост только на
`127.0.0.1`, для работы с хоста; между контейнерами публикация не нужна.

**Модель** — вне compose. Ollama работает на хосте, контейнер обращается к ней по
`host.docker.internal:11434`. Docker Desktop даёт это имя сам, а для Linux в compose добавлено
`host.docker.internal:host-gateway`. Если Ollama слушает только `127.0.0.1` и контейнер её не видит,
запустите её с `OLLAMA_HOST=0.0.0.0`.

## Образ и контейнер

**Образ** — неизменяемый шаблон: слои файловой системы плюс команда запуска. **Контейнер** —
запущенный экземпляр образа со своим слоем для записи, который исчезает вместе с ним. Из одного
образа запускаются `api`, `migrate` и `fake-llm`, меняется только команда. Данные живут не в
контейнере, а в томе `postgres_data`.

### Dockerfile

[Dockerfile](../Dockerfile) — два этапа (multi-stage):

1. **builder** ставит зависимости в виртуальное окружение из `requirements.lock`.
2. **runtime** берёт из builder только это окружение, добавляет код и запускается.

Итоговый образ не содержит ни менеджера пакетов в работе, ни кэша `pip`, ни исходников для сборки:
в нём только то, что исполняется. Это меньше и безопаснее.

### Кэш слоёв

Docker пересобирает слой, только если изменился его вход или любой слой выше. Поэтому порядок
команд важен:

```
COPY requirements.lock → RUN pip install     дорогой слой, меняется редко
COPY alembic.ini, migrations, tools, app     дешёвые слои, меняются при каждой правке
```

Если бы код копировался до установки зависимостей, каждая правка строки пересобирала бы все
зависимости. Здесь правка кода пересобирает только последние слои.

### Воспроизводимость: lock-файл

Зависимости в `pyproject.toml` без версий, и сборка «на сегодня» могла бы дать другие версии, чем
вчера. `requirements.lock` — полный список с точными версиями, включая транзитивные, собранный
`uv pip compile --universal` (одинаков для всех платформ). Образ ставится только из него. Файл
проверен: в чистом окружении по нему прошёл весь набор тестов (334) и mypy. `requirements-dev.lock`
добавляет инструменты разработки; CI ставит из него. Обновление: `uv pip compile` и прогон тестов.

### Безопасность образа

- `.dockerignore` исключает `.env`: ключи не должны попасть в образ, который копируют и публикуют.
  Секреты передаются при запуске: `env_file` и `environment` в compose.
- Процесс работает от непривилегированного пользователя `app` (uid 10001), а не от root.
- В образ не попадают тесты, документация, скрипты и `.git`.

## Завершение работы (graceful shutdown)

`docker stop` посылает `SIGTERM`, ждёт `stop_grace_period` и после этого убивает процесс. Чтобы
приложение успело завершиться чисто:

- **uvicorn — PID 1.** В `CMD` указана exec-форма (список, а не строка), поэтому сигнал приходит
  прямо в uvicorn. Через оболочку (`sh -c`) он остался бы у оболочки, и процесс убили бы по
  истечении срока вместе с запросами в работе.
- **На `SIGTERM` uvicorn** перестаёт принимать новые соединения, до 30 секунд
  (`--timeout-graceful-shutdown`) даёт доработать текущим запросам и затем выполняет завершение
  приложения: закрывает клиент модели, пул PostgreSQL и Redis (`lifespan`), а трассировка
  сбрасывает неотправленные span-ы.
- **`stop_grace_period: 45s`** больше, чем 30 секунд uvicorn: Docker не обрывает процесс,
  пока тот ещё дорабатывает.
- Запросы к модели бывают длиннее 30 секунд (три попытки по минуте). Такой запрос при остановке
  будет оборван: это известное ограничение, а не потеря: транзакции записи не начинались, пока
  шла генерация, поэтому в базе ничего не останется половинчатым.

## Проверка работоспособности контейнера

`HEALTHCHECK` обращается к `/health`, то есть проверяет живость процесса и ничего больше
([health.md](health.md)): перезапуск не вылечит недоступную базу. Для готовности к трафику
оркестратор использует `/ready`. Используется Python из образа: curl в нём нет.

## Настройки и секреты

Приложение настраивается переменными окружения (`.env.example` перечисляет все). В контейнер они
приходят из `.env` на хосте при запуске и никогда не копируются в образ. Ключи API задаются
переменной `API_KEYS` ([auth.md](auth.md)); без них приложение запускается, но все защищённые
эндпоинты отвечают 401.

## Дымовой тест

[scripts/smoke_stack.py](../scripts/smoke_stack.py) проходит по запущенному стеку: живость и
готовность, отказ без ключа, чат с сохранением в PostgreSQL, попадание в кэш Redis, повтор с
`Idempotency-Key`, стриминг, структурный ответ, 502 при сбое модели после повторов, расход и
метрики. Он же выполняется в CI ([ci.md](ci.md)).

```bash
API_KEY=<ключ с правами chat и admin> python -m scripts.smoke_stack
```

## Заглушка модели

[tools/fake_llm_server.py](../tools/fake_llm_server.py): OpenAI-совместимый сервер без GPU, который
отвечает детерминированно, умеет потоковые ответы с `usage` и структурированный вывод по схеме. Слова
`__503__`, `__429__`, `__slow__` в последнем сообщении вызывают сбой по запросу. Нужна для пробы стека и
для CI, где настоящей модели нет.

## Проверено и не проверено

- `docker compose config` подтверждает, что файл compose корректен, с профилем и без.
- Сборка образа и запуск стека на локальной машине автора не выполнялись: Docker Desktop на ней не
  запускался (требует действий в интерфейсе Windows). Сборка и дымовой тест выполняются в GitHub
  Actions на каждом запуске ([ci.md](ci.md)).
