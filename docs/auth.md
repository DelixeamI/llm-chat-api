# Аутентификация по API-ключу

Все эндпоинты, кроме `/`, `/health` и `/docs`, требуют заголовок `X-API-Key`. Код —
[app/auth.py](../app/auth.py), [app/api/security.py](../app/api/security.py).

```bash
curl.exe -X POST http://127.0.0.1:8000/v1/chat -H "X-API-Key: <ваш ключ>" -H "Content-Type: application/json" -d "..."
```

## Аутентификация и авторизация

| | Вопрос | Ответ при провале |
|---|---|---|
| **Аутентификация** | Кто вы? Ключ должен совпасть с одним из настроенных | `401 invalid_api_key` + `WWW-Authenticate: ApiKey` |
| **Авторизация** | Что вам можно? У клиента должно быть нужное право (scope) | `403 insufficient_scope` |

Реакция клиента на них разная: при 401 нужно исправить ключ, при 403 — просить больше прав.
Поэтому коды разные.

Два права:

| Scope | Что даёт |
|---|---|
| `chat` | `/v1/chat`, `/v1/chat/stream`, `/v1/chat/structured`, свои диалоги |
| `admin` | `/v1/usage`, `/v1/usage/cost`, `/v1/cache/stats`, чтение любых диалогов |

Право `admin` не даёт тратить модель: для этого нужен ещё и `chat`. Так оператору можно показать
отчёты, не открывая ему генерацию.

## Внедрение зависимостей

Проверка живёт в зависимостях FastAPI, а не в каждом обработчике:

```python
ChatClient = Annotated[Client, Depends(require_scope("chat"))]
AdminClient = Annotated[Client, Depends(require_scope("admin"))]

async def chat(request: ChatRequest, client: ChatClient, ...) -> ChatResponse:
    return await service.generate_reply(request, session, owner=client.name)
```

- `current_client` берёт заголовок и спрашивает `Authenticator`. Нет клиента — 401.
- `require_scope(...)` строится поверх неё и проверяет право. Нет права — 403.
- Обработчик получает уже готового `Client`. Забыть проверку нельзя: параметр `client` без
  зависимости не получить, а тесты перебирают все защищённые пути и ждут 401 без ключа.
- Зависимость отрабатывает **до разбора тела запроса**: анонимный клиент не узнает формат запроса
  из ошибок валидации (тест `test_invalid_key_is_rejected_before_the_request_body_is_judged`).
- Для Swagger UI объявлена схема `APIKeyHeader`: появляется кнопка Authorize.

## Секреты

- Ключи читаются из переменной окружения `API_KEYS` (JSON-список), которая лежит в `.env`; файл
  в `.gitignore`. В исходниках и в `.env.example` ключей нет, только описание формата.
- Ключ — `SecretStr`: не попадает в `repr`, логи и трассировки. Минимальная длина 16 символов.
  Тест проверяет, что отвергнутый и принятый ключи не попадают в лог.
- `Authenticator` после старта хранит только SHA-256 от ключей. Дамп памяти или случайная печать
  объекта ничего пригодного не покажет.
- **Сравнение за постоянное время:** `hmac.compare_digest` по дайджестам, без раннего выхода из
  цикла. Время проверки не говорит, какой префикс догадки верен и какая запись совпала. Хэширование
  заодно выравнивает длины, поэтому длину настоящего ключа тоже не подобрать.
- **Один ответ на пропавший и неверный ключ:** тело и код одинаковы, угадывающему не подсказать.
- **Ротация:** у клиента может быть несколько ключей. Добавьте новый, переведите клиента, удалите
  старый.
- **Ключи не заданы — API закрыт.** Без `API_KEYS` все защищённые эндпоинты отвечают 401, а при
  старте в лог пишется предупреждение. Забыть настроить ключи — значит закрыть сервис, а не открыть.

### Чего здесь нет

- Ключи хранятся в переменной окружения, а не в хранилище секретов (Vault, KMS). Для учебного
  проекта это допустимо, для эксплуатации — нет.
- Нет срока действия и отзыва ключа без перезапуска.
- Нет ограничения частоты попыток подбора ключа (день 33 ограничит частоту для известных клиентов,
  но не для неверных ключей).

## Владелец данных

Диалог и строка расхода запоминают клиента (`conversations.owner`, `usage_logs.client`, миграция
`8c3f1a52d7b4`). Правила:

- Чужой диалог для клиента выглядит как **несуществующий: 404, а не 403**. Ответ 403 подтвердил бы,
  что такой идентификатор есть, а идентификаторы как раз и перебирает злоумышленник.
- Продолжить чужой диалог нельзя ни обычным запросом, ни потоковым. Проверка идёт до вызова
  модели, поэтому никто не платит за ответ в чужом диалоге.
- Администратор **читает** любой диалог, но не **пишет** в чужой.
- Диалоги, созданные до появления владельцев, доступны только администратору: приписывать им
  владельца задним числом было бы неправдой.
- **Кэш ответов приватный:** в ключ входит владелец. Общий кэш отвечал бы за миллисекунды ровно
  тогда, когда другой клиент уже присылал такую же переписку, и так раскрывал бы чужие запросы.
  Цена: попадания между клиентами невозможны.

[test_auth.py](../tests/test_auth.py): аутентификатор (в том числе ротация и отсутствие ключей в
памяти), 401 на каждом защищённом пути, одинаковый ответ для пропавшего и неверного ключа,
