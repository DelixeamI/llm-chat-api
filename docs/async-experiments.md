# Эксперименты с асинхронностью

## Последовательные и конкурентные вызовы LLM

Скрипт: [`scripts/concurrency_experiment.py`](../scripts/concurrency_experiment.py)

```bash
python scripts/concurrency_experiment.py
```

Пять вызовов `ChatService.generate_reply` сначала по очереди через `await`, затем одновременно
через `asyncio.gather`. Во время конкурентной фазы фоновая задача каждые 50 мс отмечает «такт» —
это показывает, получает ли event loop управление, пока идут вызовы.

Условия: `qwen3:8b` в локальной Ollama на GPU, `max_tokens=120`, `temperature=0`. Перед замером
модель прогревается, а в каждой фазе свои промпты — иначе вторая фаза выигрывает за счёт кэша
промптов Ollama.

### Результаты

| Провайдер | По очереди | Одновременно | Ускорение | Тактов event loop |
|---|---|---|---|---|
| Ollama, синхронный клиент `OpenAI` | 3.30 с | 3.15 с | 1.05x | **0** |
| Ollama, асинхронный клиент `AsyncOpenAI` | 3.28 с | 3.15 с | 1.04x | 51 |
| Имитация сетевой задержки 0.6 с | 3.04 с | 0.62 с | **4.93x** | 10 |

### Выводы

**Синхронный клиент внутри `async def` блокирует event loop полностью.** Ноль тактов: пока идёт
вызов, приложение не может обработать ни один другой запрос — даже `GET /health`. `asyncio.gather`
не помогает: корутины без точек `await` на вводе-выводе выполняются строго друг за другом.

**Асинхронный клиент освобождает event loop, но не ускорил эту связку.** 51 такт — цикл всё время
был свободен. Общее время не изменилось, потому что узкое место не в клиенте, а в сервере: у
Ollama `OLLAMA_NUM_PARALLEL=1` и `n_seq_max=1` в логах — модель на одном GPU генерирует ответы
строго по одному, и запросы ждут в очереди на стороне Ollama.

**Когда задержка — это чистое ожидание ввода-вывода, конкурентность даёт почти линейный выигрыш.**
Пять вызовов по 0.6 с заняли 0.62 с. Так ведут себя облачные LLM-API: генерация идёт на чужих
серверах, а наш процесс только ждёт ответа по сети.

### Что это значит для сервиса

- Async не делает вызов LLM быстрее. Он позволяет не простаивать, пока ждём ответа, и обслуживать
  другие запросы в это время.
- Пропускная способность ограничена самым медленным звеном. Для локальной модели это GPU и
  настройка параллелизма сервера инференса, а не код приложения.
- Async не ускоряет CPU-bound работу в Python: пока корутина считает, event loop занят так же, как
  при блокирующем вызове.

## Ограничение конкурентности семафором

Скрипт: [`scripts/semaphore_experiment.py`](../scripts/semaphore_experiment.py)

```bash
python scripts/semaphore_experiment.py
```

20 одновременных запросов при лимите `LLM_MAX_CONCURRENCY=5`. Провайдер имитирует фиксированную
задержку 0.5 с и записывает момент начала каждого вызова, поэтому результат воспроизводим.

### Результаты

| Показатель | Значение |
|---|---|
| Начали выполняться сразу | 5 |
| Ждали свободного слота | 15 |
| Максимум вызовов одновременно | 5 |
| Самое долгое ожидание в очереди | 1.53 с |
| Общее время | 2.04 с (без лимита было бы около 0.5 с) |

Моменты начала вызовов идут волнами по пять: `0.00 ×5`, `0.50 ×5`, `1.01 ×5`, `1.53 ×5`.
Освободился слот — следующий запрос из очереди сразу начинает выполняться.

### Выводы

- **Семафор ограничивает число одновременных вызовов, а не частоту запросов.** Лимит 5 не говорит
  «не больше 5 запросов в минуту» — он говорит «не больше 5 вызовов в полёте в любой момент».
  Ограничение частоты по API-ключу — отдельный механизм (неделя 5).
- **Лишние запросы не отклоняются, а ждут.** Это backpressure: сервис не перегружает провайдера и
  не исчерпывает соединения, квоты и память, но задержка для клиента растёт с длиной очереди.
- **Слот удерживается на одну попытку, а не на время паузы между повторами.** Повторяющий запрос
  не блокирует других, пока спит.
- **Ожидание слота пока не ограничено по времени.** Таймаут начинает отсчёт после получения слота.
  При длительной перегрузке очередь может расти; следующий шаг — предел ожидания слота с ответом
  503.
