# Идемпотентность запросов

`POST /v1/chat` и `POST /v1/chat/structured` принимают заголовок `Idempotency-Key`. Повторный
запрос с тем же ключом и тем же телом возвращает **первый ответ**, не вызывая модель и не создавая
новых записей. Код — [app/services/idempotency.py](../app/services/idempotency.py),
[app/api/idempotency.py](../app/api/idempotency.py).

```bash
curl.exe -X POST http://127.0.0.1:8000/v1/chat -H "X-API-Key: <ключ>" -H "Idempotency-Key: order-1042" -H "Content-Type: application/json" -d "..."
```

## Зачем: ответ мог не дойти

Сеть неоднозначна. Сервер выполнил запрос, а ответ потерялся: оборвалось соединение, прокси
закрылся по таймауту, клиент упал сразу после отправки. Клиент не отличает это от «сервер запрос
не получил». Разумный клиент повторяет.

```
клиент                       сервер
  | --- POST /v1/chat ------> |  генерация, запись, расход токенов
  |           (ответ потерян) |
  | ...таймаут...             |
  | --- POST /v1/chat ------> |  без защиты: вторая генерация, вторая пара сообщений,
  |                           |  вторая строка расхода, вторая оплата
```

Повтор — не ошибка клиента, это единственно правильное поведение при неизвестном исходе. Поэтому
защита должна быть на сервере: клиент прикладывает уникальный ключ, сервер по нему узнаёт повтор.

**Идемпотентность** — свойство операции: повторный вызов даёт тот же результат, что один. `GET` и
`PUT` идемпотентны по определению, `POST` на генерацию — нет, и ключ делает его таким.

## Как это работает

| Состояние ключа | Что приходит | Результат |
|---|---|---|
| ключа нет | первый запрос | выполняется; ставится маркер «в работе» |
| «в работе» | повтор, пока первый идёт | `409 request_in_progress` + `Retry-After: 1` |
| «готово» | повтор с тем же телом | сохранённый ответ + `Idempotent-Replay: true` |
| любое | тот же ключ, **другое** тело | `422 idempotency_key_reuse` |

- **Ключ в Redis:** `llm-chat:idem:<клиент>:<sha256 ключа>`. Клиент входит в ключ: два клиента
  могут выбрать одно значение, и один не должен получить ответ другого. Сам ключ хэшируется,
  поэтому присланная клиентом строка не формирует имя ключа Redis.
- **Отпечаток запроса** — SHA-256 канонического JSON тела. Он нужен, чтобы отличить повтор от
  ошибки клиента, который переиспользовал ключ для другого вопроса: отдать ему ответ на прошлый
  вопрос было бы хуже, чем отказать.
- **Взаимное исключение — одна команда** `SET key marker NX EX 600`. Из нескольких одновременных
  запросов с одним ключом `True` получает ровно один, остальные видят маркер. Тест на настоящем
  Redis: 50 одновременных `begin` дают 1 `Proceed` и 49 `InProgress`.
- **После выполнения** маркер заменяется ответом с TTL 24 часа.
- **Ответ возвращается байт в байт** (`Idempotent-Replay: true`), включая `conversation_id` и
  расход токенов исходной генерации. Модель не вызывается, сообщения и `usage_logs` не пишутся.

## Решения и их цена

- **Сбой освобождает ключ.** Если первый запрос упал (502, 400, любая ошибка), маркер
  удаляется, и повтор действительно выполняется. Ошибки не запоминаются: иначе клиент навсегда
  получал бы сбой, случившийся один раз. Цена: повторяемый сбой повторно тратит ресурсы, но это
  то, чего клиент и ждёт.
- **Маркер «в работе» живёт 10 минут и сам истекает.** Он должен пережить самый долгий законный
  запрос, иначе повтор в середине запроса запустил бы второй. И он обязан истекать, иначе упавший
  процесс заблокировал бы ключ навсегда. Если запрос идёт дольше срока маркера, защита теряется:
  значение подобрано с запасом над худшим случаем (3 попытки по 60 с плюс паузы).
- **TTL готового ответа — сутки.** Повторы приходят за секунды и минуты, сутки — с запасом. Срок
  также ограничивает, как долго в Redis лежит ответ, который может пересказывать данные
  пользователя.
- **Redis недоступен — запросы идут без защиты** (fail open), 30 секунд пауза. Доступность важнее
  гарантии: клиент получит ответ, но повтор в этот момент уже не отсечётся. Для платёжной операции
  выбор был бы обратным.
- **Поток не поддерживается:** его нельзя ни воспроизвести из сохранённого тела, ни продолжить с
  середины. Запрос `/v1/chat/stream` с ключом получает `400 idempotency_not_supported`: честнее
  отказать, чем принять ключ и ничего не гарантировать.
- **Повтор считается в rate limit.** Иначе цикл повторов стал бы способом обойти лимит.
- **Кэш и идемпотентность — разные вещи.** Кэш ускоряет одинаковые запросы разных клиентов и
  работает только при `temperature 0`; идемпотентность защищает **один** запрос клиента от
  дублирования и работает для любой температуры.

## Известные ограничения

- Если ключ истёк посреди долгого запроса, а процесс жив, повтор запустит второе выполнение.
- Если сохранение ответа упало (Redis пропал между выполнением и записью), результат есть в БД, а
  повтор выполнится заново и создаст дубль.
- Если процесс остановили посреди запроса, ключ освободится только по истечении маркера «в работе»
  (10 минут): до этого повтор получит 409.
